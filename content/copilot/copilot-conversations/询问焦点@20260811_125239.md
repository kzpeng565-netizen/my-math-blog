- **`retrieval_mode`**（检索模式）是每次搜索请求携带的**意图标签**，由 `Query Planner` 根据用户问题推导，体现了“用户要什么类型的结果”。

---

**1. `TextbookSearchRequest`、`ResolvedSource`、`SearchContext` 等结构化协议**

- **`TextbookSearchRequest`**：由 `Query Planner` 输出的搜索请求结构体，包含了是否检索、意图模式（`retrieval_mode`）、源需求、教材/章节信息、focus 引用、用户粘贴原文等字段。它把之前零散的输入统一成一个可追踪、可审查的协议对象。
- **`ResolvedSource`**：描述**已经确定的中选来源**，包含 `source_id`、`source_type`、`confidence`、`reasons` 以及选中的 `SourceCandidate` 等。它告诉 Context Composer 和 Tutor “最终用的是哪个教材块、为什么”。
- **`SearchContext`**：传给 Tutor 的**完整检索上下文**，内含 `request`（原请求）、`resolved_source`（最终来源）、`primary_objects`（回读后的主要对象）、`supporting_dependencies`（邻居依赖）、`available_candidates`（原始候选，不展开正文）、`rendered_context`（可嵌入 Prompt 的渲染文本）、`warnings` 和 `index_status`。它让 Tutor 既能获得可读上下文，又能保留完整结构用于调试和后续分析。

这些协议取代了以往“直接把一堆字符串塞进 Prompt”的做法，实现了类型安全、可审查、可复现的检索管线。

---

**2. 检索触发、目标引用和章节信息的正确接线**

- **检索触发**：通过规则判断用户问题是否需要教材检索（如明确提到“课本”“书上”、有精确编号、或用户指定了 focus），避免之前 `SourceRequirement` 因关键词太少而完全不启动检索的问题。
- **目标引用**：`intent.target_reference` 必须传入 `TextbookSearchRequest`，不再丢弃。比如用户说“看定理2.1.5”，这个引用会被接线到精确定位模块。
- **章节信息**：会话已绑定的 `chapter_id`、`section_ref` 必须输入到搜索请求和检索器，使检索可以利用当前章节小节缩小范围，提高精度。

---

**3. 用户粘贴原文识别**

当用户粘贴完整题目（如一道习题的全文）时，系统要识别并登记为 `user_quote`，不再等待教材定位成功才能解释题目。这使检索可以把用户提供的原文作为精确匹配依据，或用于二次验证，避免因为粘贴内容找不到对应章节而直接失败。

---

**4. focus、精确标签、页码、标题定位**

这些是 **Exact Locator（精确定位器）** 的按优先级排列的定位手段：

- **focus**：UI 或用户明确指定的教材对象（如点击的题目卡片），优先级最高。
- **精确标签**：标准化后的题号/定理号，如 `Exercise 2.1.5`。
- **页码**：物理页码或 PDF 页码。
- **标题定位**：通过 heading path 或章节标题匹配。

它们共同实现了一步到位的精确定位，如果唯一且高置信，直接成为 selected source。

---

**5. 查询拆解后的 FTS5 / BM25**

之前的 FTS 直接拿整条问题作为精确短语，命中率低。v1.0 要求：

- 先对查询进行**拆解**，提取出精确标签、对象类型、英文术语、中文概念词、关系要求等。
- 然后对分解后的**关键成分**执行 FTS5 或 BM25 检索（如用 SQLite FTS5 或 BM25 排序）。
- 同时过滤掉停用词和礼貌用语，避免干扰精确短语。

这样能提高非精确查询的召回率和排序质量。

---

**6. 只对已选主要对象执行按类型正文/紧凑表示与必要邻域回读**

- 在元数据融合和 Primary Object Selection 后，**只有被选为“主要对象”的候选块**才会回读完整正文或紧凑表示。
- 回读格式按对象类型区分（如定理、例题、习题有不同的渲染方式）。
- 同时回读必要的**邻域内容**（如定理的前置定义、例题的解答步骤等）。
- 未被选中的候选只保留元数据，不占用上下文预算，避免超大 Prompt。

---

**7. `retrieval_mode` 与系统级 Retrieval Policy**

- **`retrieval_mode`**：由 Query Planner 根据问题推导的意图标签（如 `exact_reference`, `similar_examples` 等），告诉系统“用户想要什么”。
- **`RetrievalPolicy`**：系统级配置，针对每种 mode 定义了每个阶段的数量（候选 K、重排 K、最终输出 K）、主要对象类型、支撑依赖的预算等。
- 其关系：**mode 表达意图，policy 给出执行该意图时的资源分配和对象类型约束**，使检索在不同模式下自动调整粒度。

---

**8. 元数据级候选融合、去重和 Primary Object Selection**

- **候选融合**：不同检索器（精确定位、FTS/BM25、语义检索）返回的候选在**元数据层面合并**，还不包含全文。
- **去重**：根据 `source_id`、`block_id` 等去重，避免同一教材块在不同检索器中重复出现。
- **Primary Object Selection**：根据融合后的元数据（score、对象类型、与当前章节距离等）进行 rerank，并依据 `RetrievalPolicy` 中的 `active_k` 硬配额，选出最终进入上下文的 Primary Objects。

---

**9. 按对象类型选择性 hydration**

当选出 Primary Objects 后，**根据其 `object_type`**（如 theorem、example、exercise）决定回读哪些字段、以何种格式渲染，而不是对每种对象都回读相同字段。这样既能提供最有用的信息，又节省上下文预算。

---

**10. Primary Objects 与 Supporting Dependencies 的独立硬预算**

- **Primary Objects**：直接回答用户问题的主要教材对象，有独立的 `active_k_min`/`active_k_max` 预算。
- **Supporting Dependencies**：为主要对象提供上下文支撑的附属块（如前置定义、引理、概念解释），有独立的 `dependency_compact_k` 和 `dependency_full_k` 预算。
- 二者分开计算配额，避免主要对象被依赖块挤占，也防止依赖块无限膨胀。

---

**11. Current Learning State 与基础 Working Set**

- **Current Learning State**：保存会话级学习状态的结构体，记录当前教材、章节、小节、focus 对象、活跃概念、近期来源、开放问题等，并可在 UI 手动标注掌握度。
- **基础 Working Set**：从中提取出的一个**轻量对象卡片集合**（≤20 个），按角色分为 focus、active、support、recent、open_question 等。它用于指代解析、局部检索、排序特征和学习进度展示，**不把全部正文放入 Prompt**。

这两者共同为系统提供了“用户当前学到哪儿、关注什么、掌握程度如何”的状态层。

---

**12. 现有 Semantic Retriever 的统一接口、索引健康状态和安全降级**

- **统一接口**：语义检索器（如基于 embedding 的检索）暴露和精确定位、FTS 相同的候选输出接口，方便 Pipeline 无缝接入。
- **索引健康状态**：系统记录语义索引是否可用、是否过期（`index_status`），避免使用不可靠的语义结果。
- **安全降级**：当语义索引未就绪或不健康时，自动降级为仅使用精确+FTS/BM25，不断路。这是“语义就绪时启用”的前提。

---

**13. 检索 trace 与原始失败案例回归测试**

- **检索 trace**：记录每一步的请求、中间候选、融合/去重/选择结果、最终 `SearchContext` 等，用于后续调试和质量监控。
- **原始失败案例回归测试**：将之前因检索失败导致的错误案例固化为测试用例，在每次系统改动后自动运行，确保不再重现。
