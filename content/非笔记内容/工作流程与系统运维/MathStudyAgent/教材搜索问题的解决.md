要真正做成“智能检索”，核心不是把 embedding 做得更强，而是**把“指代解析”和“知识检索”拆成两个问题**。

我建议你的数学 Agent 把检索系统设计成下面这条链：

> **用户问题 → 指代解析 → 检索意图分析 → 分层候选召回 → 重排序 → 最小上下文组装 → 回答**

其中最关键的是前三层。

---

## 1. 先区分两种完全不同的检索

你说的两个需求，本质上对应：

### A. 精确指代检索

例如：

- “刚才那个例子为什么不满足条件？”
    
- “这个定理的逆命题成立吗？”
    
- “前面我们说的第二种方法呢？”
    
- “这里的 (f) 为什么连续？”
    
- “你刚才提到的反例再解释一下。”
    

这里用户其实**不是在搜索知识库**。

而是在问：

> “我说的‘这个’到底指哪个对象？”

所以应该使用一个 **Reference Resolver（指代解析器）**。

---

### B. 模糊知识检索

例如：

- “之前是不是学过一个和这个很像的定理？”
    
- “找一个能说明一致连续比连续强的例子。”
    
- “以前哪道题用过紧致性？”
    
- “我记得之前讨论过类似的证明技巧。”
    
- “有没有和这个命题相关的反例？”
    

这里才需要：

> embedding + keyword + metadata + graph 等真正的 Retrieval。

因此千万不要设计成：

> 所有问题 → embedding → top 10 → 全塞进去。

这会导致你担心的两个问题同时出现：

1. “这个定理”可能检索错。
    
2. 为了防止检索错，只能塞大量上下文。
    

---

# 2. 数学 Agent 应该存“数学对象”，而不是文本块

这是我觉得你当前设计里最值得优先确定的一件事情。

普通 RAG 经常这样切：

```text
chunk_001
chunk_002
chunk_003
```

每块 500 tokens。

但数学学习非常不适合这样。

例如你的笔记应该被解析成：

```text
Definition
Theorem
Lemma
Example
Counterexample
Proof
ProofIdea
Exercise
Solution
Technique
Question
Misconception
```

每一个都有自己的 `object_id`。

例如：

```json
{
  "id": "thm_riemann_integrable_continuous",
  "type": "theorem",
  "title": "闭区间连续函数黎曼可积",
  "statement": "...",
  "chapter": "Riemann Integral",
  "dependencies": [
    "uniform_continuity",
    "compact_interval"
  ],
  "related_examples": [...],
  "source": "数学分析笔记"
}
```

这样用户说：

> “这个定理”

Agent 找的是一个 `Theorem object`，

而不是去向量数据库里面寻找包含“定理”两个字的 chunk。

这个改变非常重要。

---

# 3. 给 Agent 建一个“当前数学工作区”

我建议不要让每次对话都从整个知识库检索。

维护一个很小的：

## Working Set

例如当前正在学：

> 一致连续

那么当前工作区可能只有：

```text
Current Topic
  一致连续

Active Objects
  def_uniform_continuity
  thm_heine_cantor
  example_x_squared
  counterexample_1_over_x

Recent Objects
  proof_heine_cantor
  question_20260810_03
```

数量可能只有 **5～15 个对象**。

---

于是用户问：

> “这个定理为什么需要闭区间？”

Reference Resolver 首先看到：

```text
最近一个 theorem:
Heine-Cantor theorem
```

于是直接解析：

```text
"这个定理"
→ thm_heine_cantor
```

根本不需要全局向量检索。

这既准确，又几乎没有上下文噪声。

---

# 4. 指代解析最好设计成“候选对象排序”

Agent 每次讲话以后，都记录出现过的数学对象。

例如最近：

```text
1. Heine-Cantor theorem
2. uniform continuity
3. f(x)=1/x
4. compactness
5. epsilon-delta proof
```

每个对象维护：

```text
last_mentioned
mention_count
object_type
conversation_role
current_topic
```

用户问：

> “这个定理的条件能不能减弱？”

系统首先识别：

```text
reference_type = theorem
```

于是候选立即变成：

```text
Heine-Cantor theorem
```

而：

```text
uniform continuity
compactness
1/x
```

直接排除。

然后计算类似：

# [  
S_{\text{ref}}

w_1S_{\text{recency}}  
+w_2S_{\text{type}}  
+w_3S_{\text{topic}}  
+w_4S_{\text{syntax}}  
]

这里甚至不一定需要 embedding。

---

# 5. 模糊检索则应该使用 Hybrid Retrieval

真正需要“搜索”的时候，再进入第二条通道。

我会推荐：

> **metadata filter + BM25 + embedding + graph expansion**

而不是纯 embedding。

例如：

> “找一下以前学过的和紧致性有关的证明。”

### 第一步：Metadata

过滤：

```text
type = proof / theorem / proof_idea
```

---

### 第二步：关键词检索

BM25：

```text
紧致
紧集
compact
compactness
```

---

### 第三步：Embedding

捕捉：

```text
有限覆盖
Bolzano-Weierstrass
Heine-Borel
列紧性
一致连续
```

这些语义联系。

---

### 第四步：知识图谱扩展

如果找到：

```text
Heine-Cantor
```

则沿关系：

```text
uses → compactness
depends_on → uniform continuity
related_to → finite subcover
```

扩展一跳。

**不要无限扩展。**

通常：

```text
0-hop
+
1-hop
```

已经足够。

---

# 6. 搜索对象最好分成四层

我非常建议你的 Agent 建这样的 Retrieval Scope：

### L0 当前消息

用户当前输入与 assistant 上一条回答。

---

### L1 当前 Working Set

当前正在学习的：

- 定义
    
- 定理
    
- 例子
    
- 证明
    
- 当前问题
    

大约 5～15 个对象。

---

### L2 当前章节

例如：

```text
数学分析
→ 一致连续
```

几十到几百个对象。

---

### L3 全局知识库

你的：

```text
数学分析
线性代数
抽象代数
拓扑
历史对话
错题
证明技巧
```

---

检索应该：

```text
L0 → L1 → L2 → L3
```

而不是：

```text
所有问题 → L3
```

---

# 7. 最关键的机制：Progressive Retrieval

这是解决“上下文太多”的核心。

例如用户问：

> “为什么这个证明不能直接取极限？”

第一次只给模型：

```text
当前问题
+
被指代的 proof
+
相关 theorem statement
```

比如总共 800 tokens。

如果模型发现：

```text
需要知道之前定义的 convergence notion
```

再主动调用：

```text
retrieve(object_id)
```

加载对应定义。

也就是说：

> **先少给，再按需扩展。**

而不是：

> “可能有用，所以全给。”

这实际上非常接近人读数学书的方式。

---

# 8. 给上下文设置三种状态

检索出来的信息不要全部正文注入。

可以分：

### Active Context

真正送给主模型。

例如：

```text
Heine-Cantor theorem
当前证明
用户的问题
```

---

### Available Context

只告诉模型：

```text
可进一步检索：
- compactness definition
- finite subcover lemma
- previous counterexample
```

但不提供内容。

---

### Background Index

完全不进入 prompt。

只有搜索工具知道。

---

因此模型看到的可能只是：

```text
ACTIVE OBJECTS

[Theorem T21]
...

[Proof P32]
...

Available references:
D12 compactness
L17 finite-subcover lemma
E29 counterexample on (0,1)
```

如果需要 E29：

```text
GET E29
```

再载入。

这样 attention 非常干净。

---

# 9. 还需要一个 Context Composer

检索到 20 个对象以后，不能简单地取 Top-K。

因为可能：

```text
top1  一个定理
top2  同一个定理的笔记
top3  同一个定理的总结
top4  同一个定理的另一个解释
```

语义非常重复。

应该加入：

## relevance + diversity + dependency

类似：

[  
S(x)=  
\alpha R(x)  
+\beta D(x)  
+\gamma C(x)  
-\lambda O(x)  
]

其中：

- (R)：与问题相关度
    
- (D)：当前推理依赖程度
    
- (C)：当前学习上下文相关性
    
- (O)：和已选内容的重复度
    

实际就是一种带数学结构的 MMR。

# 10. 数学 Agent 特别值得加入“依赖关系”

这是普通 RAG 很难做到，而你的系统可以做到的。

比如：

```text
Theorem A
    requires
        Definition B
        Lemma C

Proof A
    uses
        Technique D

Example E
    illustrates
        Definition B

Counterexample F
    disproves
        Converse of A
```

于是：

> “为什么这里可以取有限子覆盖？”

Agent 找到 proof 后发现：

```text
proof
→ uses
→ compactness
```

直接把 compactness 相关定义拉进来。

这种检索往往比 embedding 可靠得多。

# 11. 我建议最终做成三个 Retriever

架构上不要只有：

```text
Retriever
```

而是：

```text
                 User Query
                     │
               Query Analyzer
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
   Reference      Semantic     Dependency
   Retriever      Retriever    Retriever
       │              │            │
       └──────────────┼────────────┘
                      ↓
                   Reranker
                      ↓
               Context Composer
                      ↓
                    GPT
```

### Reference Retriever

解决：

> “这个”“刚才那个”“第二个方法”“前面的例子”

---

### Semantic Retriever

解决：

> “有没有类似的”“之前学过什么相关内容”

---

### Dependency Retriever

解决：

> “理解这个东西还需要哪些定义/定理？”

我认为第三个对于你的数学 Agent **尤其重要**。

# 12. Query Analyzer 可以输出一个很小的结构

例如用户：

> “刚才那个反例是不是也可以用来说明闭区间条件不能去掉？”

先解析为：

```json
{
  "intent": "analyze_example",
  "reference": {
    "expression": "刚才那个反例",
    "expected_type": "counterexample"
  },
  "concepts": [
    "closed interval"
  ],
  "retrieval_scope": "working_set",
  "need_global_search": false
}
```

Resolver：

```text
刚才那个反例
↓
counterexample_1_over_x
```

然后 Context Composer 只加入：

```text
counterexample_1_over_x
Heine-Cantor theorem
```

就够了。

# 13. 模糊问题则完全不同

例如：

> “我是不是以前见过一个类似的证明？”

Query Analyzer：

```json
{
  "intent": "recall_similar_proof",
  "reference": null,
  "retrieval_scope": "global",
  "search": {
    "type": ["proof", "proof_idea"],
    "similar_to": "current proof"
  }
}
```

这时候才调用 embedding。

# 14. 一个非常重要的原则

我会直接写进你的架构文档：

> **Reference resolution precedes semantic retrieval.**

也就是：

> **能解析指代，就不要搜索。**

其次：

> **Local retrieval precedes global retrieval.**

即：

> **能在当前工作区找到，就不要搜索整个知识库。**

最后：

> **Retrieve identifiers first, content second.**

也就是先告诉模型：

```text
可能相关：
T23
P17
E42
```

确定需要以后再加载完整内容。

这三个原则基本就能解决你说的“既智能，又不污染上下文”。
