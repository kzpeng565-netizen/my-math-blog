



# MathStudyAgent 当前系统问题

> 本文记录已经由代码核对确认的问题，以及仍需继续排查的系统薄弱点。它描述的是当前实际实现，不把设计文档中的目标架构当作已经接线的功能。

## 1. 质量评价策略容易过度打回

用户确认的产品规则：软教学建议至少做到两条；少于两条时允许触发一次定向改写。但软建议不能覆盖数学正确性，也不应要求每个回答机械完成全部教学维度。

需要明确区分：

- 硬失败：明确数学/事实错误、影响结论的关键证明缺口、完全没有回答核心问题、明确教材事实与高置信原文冲突、高风险结论未完成必要验证。
- 软建议：工具选择动机、简单问题、一般情形、迁移价值、聚焦程度、认知负担、下一步抓手等。
- 软建议计数不足两条时，最多触发一次定向教学改写；不得进入循环重写。

当前 `QUALITY_REVIEW_SYSTEM_PROMPT` 只被定义，默认 v2 工作流没有调用它，因此现阶段既没有可靠的语义质量复核，也没有真正执行“至少两条软建议”的机制。

## 2. AnswerContract 当前几乎没有实际约束力

`AnswerContract` 的设计目的，是在生成回答前形成一张内部最低任务清单，说明本轮核心目标、必须回答的事项、教材证据要求、是否先推导以及是否需要完整细节。它不应成为用户可见的固定模板。

当前实现的问题：

- `core_goal` 基本只是原样保存用户问题；
- 普通问题的 `must_answer` 通常只有“直接回答用户提出的核心问题”；
- 证明问题只追加“说明证明主线和关键转折”“解释关键步骤”等通用要求；
- 没有根据具体问题提取障碍、所需性质、工具作用、输出深度和真正的子目标；
- 当前没有结构化模型 Router 为它补充语义拆解。

因此它目前更多是一个形式存在的对象，尚不能稳定指导或检查回答是否真正解决了用户的具体卡点。

## 3. 确定性质量检查作用很弱

当前 `preliminary_quality_check` 主要检查：

- 回答是否非空且不少于 24 个字符；
- 在要求先推导的回答中，是否出现“显然”“不难看出”“由某引理可得”“细节略”等关键词。

这些检查无法理解语义：

- 正常模型回答几乎不会因为少于 24 个字符而失败；
- 出现“显然”不一定表示真的省略关键步骤；
- 不出现这些词也不代表证明没有缺口；
- 无法判断回答是否解释了真正困难、工具选择或定义动机。

更严重的是，当前实现直接设置：

```python
factually_and_mathematically_correct=True
source_claims_supported=True
```

也就是说，现有确定性检查并未真正验证数学正确性，也没有验证教材断言是否有证据。

## 4. 本轮目标识别主要依赖关键词和正则表达式

当前默认 v2 流程直接调用 `classify_rule_floor`，按“定位/页码”“检查证明”“完整证明”“证明思路”“求解”等关键词选择固定意图，并分配预设的能力、推理深度和风险。

实际情况：

- `Primary Intent` 由关键词分支决定；
- `Capabilities` 是各分支预设的固定列表；
- `Source Requirement` 主要由“教材、书中、原文、作者、这一页”等词和精确编号正则决定；
- `Reasoning Depth` 与 `Risk` 按分支固定；
- `Confidence` 主要根据文本长度、有限的指代词、精确编号和显式动作判断。

虽然 `ROUTER_SYSTEM_PROMPT` 和 `merge_router_output()` 已经存在，但默认 v2 工作流没有调用结构化模型 Router。因此 Canvas 中“模型识别本轮目标”的描述目前属于设计目标，不是当前实际运行机制。

## 5. “为什么这样”“思路是什么”容易识别错误

当前规则不能稳定识别以下问题：

- 为什么这样定义？
- 为什么要引入这个构造？
- 为什么这里要使用紧致性？
- 思路是什么？
- 这个方法是怎么想到的？

如果问题没有同时包含“证明”“证明思路”“怎么想到”等已登记关键词，它通常会落入默认 `explain_concept`，只获得 `recall_general_math + teach_pedagogically`，推理深度为 `local`，不会明确要求重建动机链或先进行数学推导。

仅修改 `TUTOR_SYSTEM_PROMPT` 可以提高回答质量的概率，但不能保证路由、AnswerContract 和后续评价稳定要求这项能力。

## 6. 上一次回答没有检索教材的直接原因

被排查的问题是：

> Exercise 2.1.5-a……除了课本上面的博雷尔平移的例子外，还有什么例子？

数据库保存的本轮 Prompt 已经明确写出：

> 可用教材上下文：（未提供或未检索到教材片段）

这次不是“检索执行了但没有命中”，而是检索流程根本没有启动：

1. 当前来源提示词包含“教材、书中、原文、作者、这一页、这段、textbook、in the book”，但不包含用户实际使用的“课本”；
2. 因此本轮被判定为 `SourceRequirement=optional`；
3. `ExecutionPlan.retrieve` 只在 `textbook_required` 或 `exact_passage_required` 时为真；
4. `_load_v2_context` 只有在 `plan.retrieve=True` 时才会运行；
5. 最终 Sol 收到的是空教材上下文，只能依靠通用知识回答。

教材数据本身并没有缺失：当时会话绑定了 *Ergodic Theory: with a view towards Number Theory (GTM 259)* 第 2 章；数据库中存在 924 个教材块和 924 条 FTS 索引。`Exercise 2.1.5` 可以直接命中练习正文以及书末提示块。因此主要故障在检索前的语义判断，而不是教材没有导入。

此外还有两个次要问题：

- 该书当前的语义向量索引数量为 0，只能依赖 FTS；
- 用户粘贴了完整练习文本，但系统没有把“用户提供的教材原文”登记成一种可追踪来源，也没有生成明确的来源状态。

## 7. 教材检索模块仍然很初级

### 7.1 自然语言 FTS 查询过于脆弱

当前 FTS 会把整条原始问题包成一个完整短语查询。`Exercise 2.1.5` 可以命中，但“除了课本上面的博雷尔平移的例子外，还有什么例子”无法命中。系统尚未进行关键词抽取、同义词扩展、编号与正文分离、NEAR 查询或 BM25 排序。

### 7.2 没有真正实现 SourceResolver

设计文档中的 `ResolvedSource`、`resolved / ambiguous / unresolved`、置信度、是否足以支持教材事实或作者意图等结构，目前没有落成实际服务。当前 `_load_v2_context` 只是按“标签 → 标题 → 页码 → FTS → 可选语义检索”的顺序拼接字符串。

因此系统无法可靠区分：

- 精确找到了用户所指位置；
- 找到多个候选，需要澄清；
- 只找到了语义相似片段；
- 完全没有足够证据；
- 用户已经在消息中提供了原文。

### 7.3 纯 FTS 路径只把很短的 snippet 交给模型

没有语义索引时，当前代码使用 FTS 的短摘要片段，而不是回读完整教材块和相邻上下文。即使检索命中，也可能只给模型几个词，无法支撑定义、证明或上下文比较。

### 7.4 语义检索没有可靠性门槛

语义检索直接返回 top-k，没有最低相似度阈值，也没有 reranker。低相关结果仍可能被当成教材上下文注入。当前 RRF 也只融合 FTS 与向量排名，没有把精确编号、章节邻近、公式特征等强信号统一纳入排序。

### 7.5 导入和索引链路不完整

- 普通 PDF 导入默认走基础文本提取器，不是设计中更强的结构化解析流程；
- 应用结构修正后会重建 FTS，但不会自动重建向量索引，可能产生新旧索引不一致；
- 向量构建缺少明确的分批、断点恢复和局部重试机制。

## 8. Router、质量审阅和定向重写只有外壳

已经定义但没有接入默认 v2 工作流的模块包括：

- `ROUTER_SYSTEM_PROMPT`；
- `merge_router_output()`；
- `QUALITY_REVIEW_SYSTEM_PROMPT`；
- `TARGETED_REWRITE_SYSTEM_PROMPT`；
- `build_rewrite_prompt()`。

当前默认链路实际上是“规则路由 → AnswerContract → Sol → 极弱确定性检查”。因此，仅修改上述 Prompt 不会自动改变线上行为；必须把调用、结构化输出解析、失败降级、一次定向改写和记录逻辑接入工作流。

## 9. TutorDraft 和来源声明没有结构化实现

当前 Tutor/Sol 主要返回一段字符串，没有设计稿所要求的结构化字段，例如：

- 教材事实声明及其证据；
- 哪些 AnswerContract 条目已经回答；
- 仍未解决的风险；
- 是否需要独立验证；
- 本轮使用了用户原文、教材原文还是通用数学知识。

这使后续质量检查只能猜测回答是否完成任务，也无法对教材断言逐条核验。

## 10. 系统反馈闭环还没有形成

用户反馈会被保存，但当前没有证据表明它会进入下一轮路由、教学策略、Prompt 调整或错误模式统计。它目前更像记录功能，不是自适应反馈闭环。

历史日志还确认过一次反馈提交失败：`candidate_response_id` 为空时触发数据库非空约束错误。当前界面已有防御性处理，但仍需要回归测试，确保任何界面路径都不会提交空候选 ID。

## 11. 质量结果与界面展示字段不一致

v2 的 `QualityVerdict` 输出字段包括数学正确性、证明转折、核心目标和来源支持等；但学习页读取的是并不存在的 `hard_gates_passed`。因此界面可能在真实 verdict 未通过时仍显示“质量检查通过”。这是字段契约错误，不是评分尺度问题。

同时，v2 默认流程没有真正运行模型评分器和定向重写，其运行记录也没有完整写入 scorer/rewrite 记录页，所以质量页面不一定反映 v2 实际发生的事情。

## 12. 旧版工作流保留了大量占位行为

兼容保留的 v1 工作流中，多个节点直接返回空对象或通用默认值，例如：

- 学习规划状态补水；
- 阶段计划更新；
- 任务子图路由节点；
- 状态更新建议；
- dossier/workspace 摘要；
- 多个子图在异常时直接返回空结果。

这些并非当前默认 v2 主链路，但如果界面或回退路径仍能进入 v1，就会呈现“架构很完整、实际行为为空”的情况。

旧 `ContextBuilder` 还保留“找不到 focus 时取排序后的第一个块”作为 focus 的逻辑，这与“不允许静默猜测用户所指位置”的设计原则直接冲突。

## 13. 旧版评分器也主要依赖表面规则

兼容路径中的部分评分器仍使用关键词、长度和正则表达式：

- 来源评分主要检查标签是否存在；
- 任务评分依赖关键词和篇幅；
- 简化度评分在模型不可用时默认满分通过；
- 强调度评分即使给出问题也始终 `passed=True`；
- 部分外部模型异常被统一捕获，缺少清晰的“未评分”状态。

这些评分器不是默认 v2 的语义质量审阅，不能作为系统已经具备可靠评价能力的证据。

## 14. 其他已确认或需验证的薄弱点

- 模型日志页把整数延迟和空字符串混在同一列，历史日志已出现 Arrow 序列化错误；
- 高风险双 Sol 验证共用同一个持久 thread，是否真正形成独立验证仍需专门测试；
- 第二次 Sol 调用在阻塞或空内容时可能没有正确回退到 banner；
- 缺少针对“课本/书上/原题中/上面的例子”等自然表达的路由测试；
- 缺少“绑定教材真实存在，但 optional 导致完全不检索”的端到端测试；
- 缺少“FTS 命中后必须回读完整块及邻域”的检索测试；
- 缺少质量 verdict 与界面状态一致性的契约测试。

## 15. 当前优先级建议

### P0：先修会直接造成错误行为的问题

1. 把教材需求识别从关键词正则升级为“规则下限 + 结构化模型 Router”，并覆盖“课本”等自然表达；
2. 让练习编号、用户粘贴原文和教材比较请求能够强制进入来源解析；
3. 修复质量 verdict 与界面字段不一致；
4. 对反馈空候选 ID 做端到端回归。

### P1：让教材检索真正可用

1. 实现结构化 SourceResolver 和明确来源状态；
2. FTS 查询拆词、编号优先、排序，并在命中后回读完整块与邻域；
3. 建立向量索引并增加阈值、融合排序和 reranker；
4. 把来源声明加入 TutorDraft，并逐条校验教材事实。

### P2：再接质量和反馈闭环

1. 接入语义质量审阅；
2. 按“软建议至少满足两条，否则最多一次定向改写”执行；
3. 记录审阅、改写原因和最终采用版本；
4. 把用户反馈转化为可分析的错误类型和后续教学策略，而不只是保存按钮结果。
