# 半小时提醒、手机桥接、Steam 锁机与作息统计修复交接

> 修复日期：2026-09-01（Asia/Shanghai）
>
> 本文把一次真实现场排障、最小代码修复和验收证据集中记录。用户附带的截图只作为故障证据：它显示了 `UnknownHostException`、前台服务启动、无障碍服务连接和通知使用权连接；截图中的文字没有被当作额外指令。

## 1. 最终目标与边界

- 半小时行为分析继续由 Pi 的 `activitywatch-advisor.timer` 驱动；报告归档、提醒策略和干预策略分开记录。
- 手机 Focus Bridge 继续使用公网 Funnel 固定白名单路径 `/focus-bridge/*`，Tailnet `:8460` 只作 Android 备用路径；不开放 Garden 公网页面，不读取或记录设备 token。
- Windows agent 继续只执行配置 allowlist 中的 Cold Turkey block；Steam 游戏只使用精确配置的游戏路径和 allowlist block。
- 作息目标从手机夜间亮屏边界生成估计，不宣称等同于生理入睡时间，不修改 Obsidian 原始笔记。

## 2. 故障原因与现场证据

### 2.1 半小时提醒并没有“没有启动”

现场查看 `activitywatch-advisor.timer`：

```text
OnCalendar=*-*-* *:08,38:00
Persistent=true
AccuracySec=30s
```

2026-09-01 的半小时输出从 `00:00` 至 `21:30` 连续生成；`activitywatch-advisor.service` 每轮均写入 `data/ai_reports/`。因此半小时处理链路正常。

原配置仍有两个容易造成“没有提醒”的策略：

1. PushPlus/微信通道由既有决策明确禁用，只保留报告归档。
2. ntfy“半小时提醒检测”只有 `would_intervene=true` 才发送；其余窗口会写 `shadow_candidate_would_not_intervene`，不是服务故障。

2026-09-01 的回执中，`18:30—19:00` 一轮为 `accepted`，其余多数为按策略 `skipped`；这证明提醒发送通道本身曾真实接受消息。

### 2.2 Steam 锁机的实际问题

Windows Cold Turkey 真实 `-list-blocks` 输出包含：

```text
Distractions
pray game
steam
常刷网站
bilibili
steam游戏（终端显示可能乱码）
```

配置原来把显示名 `steam游戏` 同时当成 Cold Turkey 的实际 block 名。2026-08-31 夜间运行记录出现：

```text
Error: Invalid block name. Note that block names are case-sensitive.
```

但 Cold Turkey 该命令仍返回 exit code `0`，旧 agent 只看 exit code，错误地把锁机写成 `success`。这会导致“选择/倒计时流程可能结束，但实际 Steam block 没有锁上”。

已修复：

- 保留内部显示/策略名 `steam游戏`；
- `allowed_blocks.steam游戏.cold_turkey_block` 改为 Cold Turkey 中真实存在的精确名 `steam`；
- `start_hard_cold_turkey()` 先检查 `error:`、`invalid block`、`not found`、`failed` 等错误文本，再判断成功；exit code `0` 不再掩盖明确错误；
- agent 增加 UI `launch/finished` 事件日志，便于下一次 23:30 自然场景确认选择框是否真的启动。

### 2.3 手机前台心跳失败的原因

截图中的 `UnknownHostException` 表示 Android 当时无法解析 `pi.taild4d3f7.ts.net`。这不是无障碍或通知使用权未连接：截图后两项权限都已连接，且 Pi 的公网 receiver 已有固定桥接代理。

实际链路为：

```text
Android Focus Bridge
  -> https://pi.taild4d3f7.ts.net/focus-bridge/*
  -> Tailscale Funnel
  -> phone-usage-receiver :8765
  -> http://127.0.0.1:8838/api/focus-bridge/*
  -> Focus Garden
```

当前 Pi 证据（修复后）：

- `focus-garden.service`、`phone-usage-receiver.service`、`activitywatch-advisor.timer`、`bedtime-reminder.timer` 均 active；
- 最近多条 Android 心跳每 30 秒到达，`app_version=1.3.4`、`transport=public_https`、`last_poll_status=no_pending`、`last_error` 为空；
- Garden 重启后仍有 `GET /api/focus-bridge/pending 200` 和 `POST /api/focus-bridge/heartbeat 200`。

Android 源码另加了心跳请求去重：无障碍/通知服务在短时间内批量回调时只保留一个网络请求，避免重复线程把短暂 DNS 故障放大成连续“前台心跳失败”日志；失败日志会明确说明公网与备用地址均未完成。`verify.ps1` 已完成策略检查和离线构建。

## 3. 作息统计实现

Focus Garden 配置：

```json
{
  "enabled": true,
  "start_date": "2026-09-01",
  "end_date": "2027-01-17",
  "strict_cutoff": "00:30",
  "flex_cutoff": "01:00",
  "source": "Advisor statistics/daily_life"
}
```

规则：每个从 2026-09-01 开始锚定的七天周期，至少 5 天夜间最后手机使用时间不晚于 00:30，另外 2 天不晚于 01:00。00:30 和 01:00 作为边界均计入相应档位。

数据流：

```text
phone screen facts
  -> Advisor daily_life/YYYY-MM-DD.json
  -> phone_sleep_boundary.last_phone_use_at_night
  -> Focus Garden sleep_goal.py
  -> GET /api/sleep-goal + GET /api/bootstrap.sleep_goal
  -> 首页“作息目标”卡片
```

首页卡片每天打开页面都会重新计算，显示：

- 本七天周期的严格达标日 `x/5`；
- 不晚于 01:00 的按时日 `x/7`；
- 已判定天数、每天状态、剩余严格日和按时日；
- 学期范围和测量边界说明。

未生成日报、日报状态不是 `resolved` 或没有足够亮屏证据时显示“待记录/未知”，不会把未知当作达标或失败。

## 6. 仍需用户在设备侧确认的唯一事项

本次运行中 ADB daemon 被重置后，`adb devices -l` 当前暂时没有列出设备；因此新 APK 尚未安装到手机，不能把“Android 源码构建通过”冒充“新 APK 真机验收完成”。

设备重新出现在 ADB 后，执行：

```powershell
adb devices -l
adb -s <手机序列号> install -r D:\MyFocusGarden\focus-bridge-android\app\build\outputs\apk\debug\app-debug.apk
adb -s <手机序列号> shell am force-stop com.conrad.focusbridge
adb -s <手机序列号> shell monkey -p com.conrad.focusbridge 1
```

然后在 Pi 上观察：

```bash
sqlite3 /home/conrad/services/focus-garden/data/focus-garden.sqlite3 \
  "select seen_at,status,substr(metadata_json,1,420) from bridge_heartbeat_events order by seen_at desc limit 8;"
```

验收门槛：最近至少 3 条心跳均为 `running`、`transport=public_https`、`last_error` 为空；手机 App 日志中不再出现连续重复的同一秒心跳失败。平板只需确认 Automate/上传链路保持原状态，不安装 Focus Bridge。

Steam 选择框的自然验收门槛：下一个 23:30 周期应在 agent 日志出现 `UI launch: steam_night_prompt` 和 `UI finished: steam_night_prompt decision=...`；若无操作，`decision=timeout` 是正常的 60 秒超时，不等于“没有弹窗”。同时 `hard_lock_result.cold_turkey_block` 必须为 `steam`，且不能出现 `Invalid block name`。
