# 手机使用记录系统——树莓派端操作与维护指南

<!-- ai_provenance: source=codex; date=2026-07-24; verification=checked; retrieved_notes="" -->

> [!summary]
> 本文记录树莓派上的手机使用记录接收、验证、归档、压缩、清理与故障恢复流程。配置状态以 2026-07-24 的已部署系统为准。

配套文档：[[手机使用记录系统——手机端操作与维护指南]]

## 1. 系统职责

树莓派端负责：

- 通过 HTTPS 接收手机上传的三个 JSONL 文件；
- 验证上传密钥、文件名、大小、UTF-8、JSON 和时间戳；
- 按事件时间将数据归入日期目录；
- 合并、去重并按时间排序；
- 原子替换文件，避免中途断电留下半个文件；
- 保存最近一次上传镜像；
- 归档满 30 天后压缩；
- 删除超过 365 天的原始日期归档；
- 为后续分类统计、ActivityWatch 合并和可视化提供数据源。

树莓派端目前不负责：

- 手机限制或锁定；
- AI 判断学习与娱乐；
- 应用包名分类汇总；
- 半小时统计输出；
- Windows ActivityWatch 合并；
- 自动向 PushPlus 报告上传失败。

这些属于后续处理层，不应塞进接收程序。

## 2. 架构

```text
Android Automate
    │
    │ HTTPS PUT + X-Upload-Token
    ▼
Tailscale Funnel
https://pi.taild4d3f7.ts.net:443
    │
    │ 反向代理
    ▼
127.0.0.1:8765
phone-usage-receiver.service
    ├─ incoming/        最近一次上传镜像
    └─ archive/日期/    合并后的长期归档
```

接收端只监听：

```text
127.0.0.1:8765
```

外部设备不能通过树莓派局域网 IP 直接访问 8765。公网 HTTPS 只由 Tailscale Funnel 提供。

## 5. 服务和文件

### 5.1 systemd 服务

| 组件 | systemd 单元 | 状态 |
|---|---|---|
| 手机数据接收 | `phone-usage-receiver.service` | enabled、active |
| 归档维护 | `phone-usage-maintenance.service` | oneshot |
| 维护定时器 | `phone-usage-maintenance.timer` | enabled、active |
| Tailscale | `tailscaled.service` | enabled、active |

### 5.2 文件结构

```text
/home/conrad/phone_usage/
├─ receiver.py
├─ maintenance.py
├─ token.txt
├─ incoming/
│  ├─ foreground.jsonl
│  ├─ screen.jsonl
│  └─ heartbeat.jsonl
└─ archive/
   ├─ YYYY-MM-DD/
   │  ├─ foreground.jsonl
   │  ├─ screen.jsonl
   │  └─ heartbeat.jsonl
   └─ 更早日期/
      ├─ foreground.jsonl.gz
      ├─ screen.jsonl.gz
      └─ heartbeat.jsonl.gz
```

核心路径：

```text
接收程序：/home/conrad/phone_usage/receiver.py
维护程序：/home/conrad/phone_usage/maintenance.py
上传密钥：/home/conrad/phone_usage/token.txt
最新镜像：/home/conrad/phone_usage/incoming/
长期归档：/home/conrad/phone_usage/archive/
```

权限要求：

- `token.txt` 应为 `600`；
- 数据文件应为 `600`；
- `archive` 目录应仅允许 `conrad` 访问；
- 服务以 `conrad` 身份运行，不以 root 运行。

> [!important]
> `incoming/` 只是最近一次请求正文的镜像，可能是空文件、当天部分文件或一次旧文件补传。长期数据的权威来源是 `archive/YYYY-MM-DD/`。

## 6. HTTP 接口

### 6.1 健康检查

```text
GET /health
```

成功响应：

```json
{"ok":true,"service":"phone-usage"}
```

本机测试：

```bash
curl http://127.0.0.1:8765/health
```

公网测试：

```bash
curl https://pi.taild4d3f7.ts.net/health
```

健康检查不需要上传密钥，只表示 Funnel、代理和接收进程可达，不表示手机文件一定在增长。

### 6.2 上传接口

```text
PUT /upload/foreground.jsonl
PUT /upload/screen.jsonl
PUT /upload/heartbeat.jsonl
```

也支持 `POST`，但手机当前使用 `PUT`。

请求头：

```text
X-Upload-Token: <私有密钥>
```

允许的目标文件名只有：

```text
foreground.jsonl
screen.jsonl
heartbeat.jsonl
```

不允许任意路径或文件名。

### 6.3 返回状态

常见状态：

| 状态 | 含义 |
|---:|---|
| 200 | 验证通过并已保存 |
| 400 | 文件名、内容长度、UTF-8、JSONL 或时间戳无效 |
| 401 | 上传密钥错误或缺失 |
| 411 | 缺少 `Content-Length` |
| 413 | 上传超过大小限制 |
| 404 | 未知路径或不允许的文件名 |

单次上传上限：

```text
20 MiB
```

## 7. 接收与归档逻辑

接收程序按以下顺序处理请求：

1. 只接受 `/upload/` 下三个白名单文件名；
2. 使用恒定时间比较验证 `X-Upload-Token`；
3. 检查 `Content-Length` 和 20 MiB 上限；
4. 读取完整请求正文；
5. 验证 UTF-8；
6. 逐行解析 JSON；
7. 要求每行是对象且包含可解析的 `timestamp`；
8. 根据时间戳的本地日期分组；
9. 与相同日期、相同类型的现有归档合并；
10. 对完全相同的 JSON 事件去重；
11. 按时间排序；
12. 使用临时文件、`fsync` 和原子替换保存；
13. 将原请求正文写入 `incoming/`。

因此：

- 重复上传整个文件不会产生重复归档；
- 手机断网后恢复并重新上传完整文件，可以补齐数据；
- 新日期文件只有少量记录时，不会覆盖当天较早的归档；
- 旧版无日期累计文件可以安全补传；
- 空文件只更新 `incoming/`，不会清空已有日期归档。

## 8. 数据模型

### 8.1 前台应用事件

必需字段：

```json
{
  "timestamp": "2026-07-24T17:00:00+08:00",
  "device": "phone",
  "event": "foreground",
  "package": "com.tencent.mm"
}
```

### 8.2 屏幕状态事件

```json
{
  "timestamp": "2026-07-24T17:05:00+08:00",
  "device": "phone",
  "event": "screen",
  "state": "off"
}
```

`state` 为：

```text
on
off
```

### 8.3 心跳

```json
{
  "timestamp": "2026-07-24T17:15:00+08:00",
  "device": "phone",
  "event": "heartbeat"
}
```

当前接收器严格验证 JSON 和时间戳，但没有严格限制其他字段取值。下游统计程序仍应再次检查 `event`、`state` 和 `package`。

### 9.1 一条命令检查服务

```bash
  phone-usage-receiver.service \
  phone-usage-maintenance.timer \
  tailscaled.service
```

三个结果都应为：



```text

```

若出现 `0.0.0.0:8765`，说明接收器直接暴露到局域网，应立即检查 `receiver.py` 的 `HOST`。

### 9.3 检查最近上传

```bash

  -u phone-usage-receiver.service \
  --since "1 hour ago" \
  --no-pager
```

正常每轮应出现三条：

```text
"PUT /upload/foreground.jsonl HTTP/1.1" 200
"PUT /upload/screen.jsonl HTTP/1.1" 200
"PUT /upload/heartbeat.jsonl HTTP/1.1" 200
```

### 9.4 检查最新镜像

```bash
ls -lh --time-style=long-iso \
  /home/conrad/phone_usage/incoming/*.jsonl
```

```bash
wc -l /home/conrad/phone_usage/incoming/*.jsonl
```

注意：前台和屏幕文件在当天尚无事件时可以是 0 行。

### 9.5 检查当天归档

```bash
today="$(date +%F)"
ls -lh "/home/conrad/phone_usage/archive/$today/"
wc -l "/home/conrad/phone_usage/archive/$today/"*.jsonl
```

心跳应持续增加。若归档心跳不增长，而手机本地增长，优先检查上传和网络。

### 9.6 验证 JSONL

```bash
python3 - <<'PY'
from pathlib import Path
import json

root = Path("/home/conrad/phone_usage/archive")
for path in sorted(root.glob("*/*.jsonl")):
    count = 0
    for number, line in enumerate(
        path.read_text(encoding="utf-8").splitlines(),
        start=1,
    ):
        if not line.strip():
            continue
        json.loads(line)
        count += 1
    print(path, count)
PY
```

该检查只解析，不修改文件。

## 11. 归档维护

### 11.1 当前策略

```text
归档满 30 天：将 .jsonl 压缩为 .jsonl.gz
归档超过 365 天：删除整个日期目录
```

“满 30 天”按目录日期与树莓派本地日期之差计算。

### 11.2 定时器

当前配置：

```text
OnCalendar=*-*-* 03:30:00
Persistent=true
RandomizedDelaySec=15m
```

实际运行时间通常在：

```text
03:30—03:45
```

若计划时间树莓派关机，`Persistent=true` 会在下次启动后补跑。

查看下次执行：

```bash
systemctl list-timers phone-usage-maintenance.timer --no-pager
```

### 11.3 手动试运行

```bash
sudo systemctl start phone-usage-maintenance.service
```

查看结果：

```bash
journalctl \
  -u phone-usage-maintenance.service \
  -n 50 \
  --no-pager
```

手动运行不会压缩未满 30 天的文件。

### 11.4 检查压缩文件

```bash
find /home/conrad/phone_usage/archive \
  -type f \
  -name '*.jsonl.gz' \
  -print
```

验证 gzip：

```bash
gzip -t /home/conrad/phone_usage/archive/YYYY-MM-DD/*.jsonl.gz
```

读取但不解压到磁盘：

```bash
zcat /home/conrad/phone_usage/archive/YYYY-MM-DD/heartbeat.jsonl.gz | tail
```

### 11.5 修改保留策略

维护程序中的常量：

```python
COMPRESS_AFTER_DAYS = 30
DELETE_AFTER_DAYS = 365
```

修改流程：

1. 备份 `maintenance.py`；
2. 修改本地副本；
3. 运行 `python3 -m py_compile`；
4. 安装到正式路径；
5. 手动启动一次维护服务；
6. 检查日志和归档；
7. 更新本文。

不要直接在未备份的正式文件上试错。

## 12. Tailscale 与 Funnel

### 12.1 查看 Tailscale

```bash
systemctl status tailscaled.service --no-pager
tailscale status
```

### 12.2 查看 Funnel

```bash
tailscale funnel status
```

正常应显示：

```text
https://pi.taild4d3f7.ts.net
|-- / proxy http://127.0.0.1:8765
```

### 12.3 Funnel 失效

依次检查：

```bash
systemctl is-active tailscaled.service
tailscale status
tailscale funnel status
curl http://127.0.0.1:8765/health
curl https://pi.taild4d3f7.ts.net/health
```

判断：

- 本机健康检查失败：接收器问题；
- 本机成功、公网失败：Tailscale 或 Funnel 问题；
- 两者成功、手机失败：手机网络、Clash、DNS 或 Automate 配置问题。

### 12.4 安全边界

Funnel 是公网入口。必须保持：

- 8765 只监听回环地址；
- 上传接口始终要求密钥；
- 路由器不做 8765 端口转发；
- 不在文档或仓库记录真实密钥；
- 不开放 Cockpit、File Browser 或 SSH 到 Funnel；
- 定期检查未知请求和 401。

公网扫描器访问常见路径是正常现象。未知路径应返回 404，错误密钥应返回 401。

## 13. 上传密钥

密钥文件：

```text
/home/conrad/phone_usage/token.txt
```

检查权限，不显示内容：

```bash
stat -c '%a %U %G %n' /home/conrad/phone_usage/token.txt
```

期望：

```text
600 conrad conrad
```

### 13.1 什么时候轮换

- 密钥出现在截图、聊天或公开仓库；
- 手机丢失；
- 怀疑有未授权上传；
- 管理人员变化；
- 定期安全维护。

### 13.2 安全轮换步骤

1. 停止手机 Automate 流程；
2. 在树莓派生成新密钥到临时文件；
3. 原子替换 `token.txt`；
4. 重启接收服务；
5. 在手机三个 HTTP request 中更新请求头；
6. 启动手机流程；
7. 验证三次 200；
8. 确认旧密钥返回 401。

生成时不要把密钥写入 shell 历史或本文。可以在树莓派本地交互式执行并直接复制到手机：

```bash
umask 077
openssl rand -hex 32 > /home/conrad/phone_usage/token.txt.new
mv /home/conrad/phone_usage/token.txt.new \
  /home/conrad/phone_usage/token.txt
sudo systemctl restart phone-usage-receiver.service
```

随后通过树莓派本地终端查看并复制，完成后清除终端显示。

## 16. 故障诊断

### 16.1 服务无法启动

```bash
systemctl status phone-usage-receiver.service --no-pager -l
journalctl -u phone-usage-receiver.service -n 100 --no-pager
python3 -m py_compile /home/conrad/phone_usage/receiver.py
```

常见原因：

- Python 语法错误；
- `token.txt` 缺失或无读取权限；
- 8765 被其他进程占用；
- systemd 硬化规则与写入路径不一致；
- 文件所有者错误。

### 16.2 端口被占用

```bash
ss -lntp | grep ':8765 '
```

不要直接杀未知进程。先确认 PID、程序和服务归属。

### 16.3 手机收到 401

```bash
journalctl \
  -u phone-usage-receiver.service \
  --since "30 minutes ago" \
  --no-pager
```

确认手机三个 HTTP request 都使用同一新密钥。不要在日志或文档中打印密钥。

### 16.4 手机收到 400

接收器响应通常包含错误类型和行号。检查：

- 是否为 UTF-8；
- 每行是否是独立 JSON；
- 是否有空字段或缺少 `timestamp`；
- 时间戳是否为 ISO 8601；
- 上传 URL 文件名是否为白名单之一。

### 16.5 归档行数突然减少

当前接收器使用合并去重，不应因上传小文件而减少。

立即执行：

```bash
wc -l /home/conrad/phone_usage/archive/YYYY-MM-DD/*.jsonl
ls -l /home/conrad/phone_usage/receiver.py*
journalctl -u phone-usage-receiver.service --since today --no-pager
```

停止修改，不要继续覆盖；检查是否错误恢复了旧版接收器。必要时从备份恢复程序，并从手机旧文件重新补传。

### 16.6 心跳缺失

判断顺序：

1. 手机本地心跳是否增长；
2. 手机是否记录上传失败；
3. 公网健康检查是否成功；
4. 接收服务是否 active；
5. Funnel 是否开启；
6. 归档当天心跳最后时间；
7. 手机是否被后台管理杀死。

### 16.7 磁盘空间不足

```bash
df -h /
du -sh /home/conrad/phone_usage/*
du -sh /home/conrad/phone_usage/archive/* | sort -h | tail
```

不要直接递归删除整个 `phone_usage`。先确认最大日期目录、备份状态和保留策略，再删除明确的旧日期目录。

### 16.8 树莓派降频或供电异常

```bash
vcgencmd get_throttled
```

正常：

```text
throttled=0x0
```

非零时检查电源、线材、温度和系统日志。

## 17. 恢复流程

### 17.1 程序损坏但数据完好

1. 停止接收服务；
2. 恢复最近验证过的 `receiver.py`；
3. 检查语法；
4. 启动服务；
5. 检查本地和公网健康接口；
6. 从手机重新上传完整日期文件；
7. 检查归档合并结果。

### 17.2 归档误删

1. 立即停止维护定时器：

```bash
sudo systemctl stop phone-usage-maintenance.timer
```

2. 不要向原目录写入无关文件；
3. 从最近备份恢复到临时目录；
4. 校验 JSONL 或 gzip；
5. 比较日期和行数；
6. 只恢复缺失的明确日期；
7. 重新启动定时器。

### 17.3 token 丢失

无法从文档恢复。应按第 13 节生成新密钥，同时更新手机三个请求头。

## 19. 当前限制与改进方向

### 19.1 缺少完整性摘要

目前响应返回文件名、字节数、行数和日期，但没有 SHA-256。可增加：

- 手机计算或服务器返回文件哈希；
- 上传成功记录保存哈希；
- 每日一致性报告。

### 19.2 缺少自动告警

目前只能通过心跳间隔和日志发现中断。可增加独立监控：

- 30 分钟无心跳时 PushPlus 通知；
- 接收服务失败时 systemd `OnFailure` 通知；
- 磁盘使用率超过阈值通知；
- Funnel 不可达通知。

告警程序不得读取或发送上传密钥。

### 19.3 没有下游汇总

建议另建只读处理程序：

```text
archive JSONL
→ 连续事件去重
→ 根据下一个事件计算持续时间
→ 用 screen off/on 修正
→ 应用包名分类
→ 生成半小时和每日摘要
```

处理程序不应修改原始归档。

### 19.4 跨午夜手机尾部缺口

这是手机上传策略问题，参见手机端指南第 15 节。服务器已经能合并昨天与今天的数据，但手机尚未自动补传昨天文件。

### 19.5 备份尚未自动化

当前归档维护只压缩和删除，不等于备份。应为 `/home/conrad/phone_usage/archive` 建立独立备份策略，并定期做恢复演练。
