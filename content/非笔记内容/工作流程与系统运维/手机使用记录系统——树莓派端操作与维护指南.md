# 手机使用记录系统——树莓派端操作与维护指南

## 1. 系统架构

```text
Android Automate
    │
    │ HTTPS PUT + X-Upload-Token
    ▼
Tailscale Funnel
https://pi.taild4d3f7.ts.net:443
    │
    │ 反向代理
    ▼
127.0.0.1:8765
phone-usage-receiver.service
    ├─ incoming/        最近一次上传镜像
    └─ archive/日期/    合并后的长期归档
```

树莓派端只负责：

- 接收手机上传的三个 JSONL 文件；
- 验证上传密钥、文件名、大小、JSON 和时间戳；
- 按事件日期归档；
- 合并、去重并按时间排序；
- 原子写入，避免不完整文件；
- 定期压缩和清理旧归档。

应用分类、使用时长计算、ActivityWatch 合并和 AI 分析属于后续处理层，不放入接收服务。

## 2. 当前关键配置

### 2.1 地址与服务

```text
Tailscale MagicDNS：pi.taild4d3f7.ts.net
公网入口：https://pi.taild4d3f7.ts.net
Funnel 转发：http://127.0.0.1:8765
接收服务：phone-usage-receiver.service
维护定时器：phone-usage-maintenance.timer
Tailscale 服务：tailscaled.service
```

接收程序必须只监听：

```text
127.0.0.1:8765
```

不要把 8765 改为 `0.0.0.0`，也不要在路由器上转发该端口。

### 2.2 文件位置

```text
/home/conrad/phone_usage/
├─ receiver.py
├─ maintenance.py
├─ token.txt
├─ incoming/
│  ├─ foreground.jsonl
│  ├─ screen.jsonl
│  └─ heartbeat.jsonl
└─ archive/
   └─ YYYY-MM-DD/
      ├─ foreground.jsonl
      ├─ screen.jsonl
      └─ heartbeat.jsonl
```

超过压缩期限后，归档文件扩展名变为：

```text
.jsonl.gz
```

重要区别：

- `incoming/` 是最近一次上传的原始请求镜像，可能为空或只含部分数据；
- `archive/YYYY-MM-DD/` 是长期数据的权威来源。

### 2.3 密钥

上传密钥位于：

```text
/home/conrad/phone_usage/token.txt
```

文件权限应为：

```text
600 conrad conrad
```

真实密钥只能保存在该文件和手机 Automate 的请求头中，不能写入本文、Git、截图或聊天。

## 3. HTTP 接口

### 3.1 健康检查

```text
GET /health
```

正常响应：

```json
{"ok":true,"service":"phone-usage"}
```

### 3.2 上传接口

```text
PUT /upload/foreground.jsonl
PUT /upload/screen.jsonl
PUT /upload/heartbeat.jsonl
```

请求头：

```text
X-Upload-Token: <私有密钥>
```

只允许上述三个文件名，单次上传上限为 20 MiB。

常见状态：

| 状态 | 含义 |
|---:|---|
| 200 | 验证通过并已保存 |
| 400 | JSONL、时间戳、编码或请求内容有误 |
| 401 | 上传密钥错误或缺失 |
| 404 | 路径或文件名不在白名单 |
| 411 | 缺少 `Content-Length` |
| 413 | 文件超过大小限制 |

## 4. 接收与归档逻辑

每次上传按以下顺序处理：

1. 检查 URL 中的文件名是否在白名单；
2. 验证 `X-Upload-Token`；
3. 检查文件大小；
4. 验证 UTF-8；
5. 逐行解析 JSON；
6. 要求每个事件包含可解析的 `timestamp`；
7. 按时间戳所属日期分组；
8. 与相同日期、相同类型的现有归档合并；
9. 删除完全相同的重复事件；
10. 按时间排序；
11. 使用临时文件、`fsync` 和原子替换保存；
12. 将原请求写入 `incoming/`。

由此保证：

- 重复上传完整文件不会制造重复归档；
- 手机断网后重新上传可以补齐数据；
- 新日期文件刚创建、记录较少时不会覆盖当天旧数据；
- 旧版无日期文件仍可补传；
- 上传空文件不会清空已有归档。

## 5. 数据格式

### 5.1 前台应用

```json
{"timestamp":"2026-07-24T17:00:00+08:00","device":"phone","event":"foreground","package":"com.tencent.mm"}
```

### 5.2 屏幕状态

```json
{"timestamp":"2026-07-24T17:05:00+08:00","device":"phone","event":"screen","state":"off"}
```

### 5.3 心跳

```json
{"timestamp":"2026-07-24T17:15:00+08:00","device":"phone","event":"heartbeat"}
```

每一行必须是一个完整 JSON 对象。接收端会验证 JSON 和时间戳；下游统计程序仍应验证 `event`、`state` 和 `package` 的取值。

## 6. 归档保留策略

维护定时器每天约在：

```text
03:30—03:45
```

执行：

```text
归档满 30 天：.jsonl → .jsonl.gz
归档超过 365 天：删除整个日期目录
```

定时器使用 `Persistent=true`，如果计划时间树莓派关机，会在下次启动后补跑。

关键常量位于：

```text
/home/conrad/phone_usage/maintenance.py
```

```python
COMPRESS_AFTER_DAYS = 30
DELETE_AFTER_DAYS = 365
```

修改保留策略后，应手动试运行一次：

```bash
sudo systemctl start phone-usage-maintenance.service
journalctl -u phone-usage-maintenance.service -n 30 --no-pager
```

## 7. 专项检查

### 7.1 检查核心服务

```bash
systemctl is-active \
  phone-usage-receiver.service \
  phone-usage-maintenance.timer \
  tailscaled.service
```

三个结果都应为：

```text
active
```

### 7.2 检查监听和 Funnel

```bash
ss -lntp | grep ':8765 '
tailscale funnel status
```

预期：

```text
127.0.0.1:8765
https://pi.taild4d3f7.ts.net
|-- / proxy http://127.0.0.1:8765
```

### 7.3 检查健康接口

树莓派本机：

```bash
curl http://127.0.0.1:8765/health
```

公网入口：

```bash
curl https://pi.taild4d3f7.ts.net/health
```

两者均应返回：

```json
{"ok":true,"service":"phone-usage"}
```

### 7.4 检查最近上传

```bash
journalctl \
  -u phone-usage-receiver.service \
  --since "1 hour ago" \
  --no-pager
```

每轮正常上传应出现：

```text
"PUT /upload/foreground.jsonl HTTP/1.1" 200
"PUT /upload/screen.jsonl HTTP/1.1" 200
"PUT /upload/heartbeat.jsonl HTTP/1.1" 200
```

### 7.5 检查当天归档

```bash
today="$(date +%F)"
ls -lh "/home/conrad/phone_usage/archive/$today/"
wc -l "/home/conrad/phone_usage/archive/$today/"*.jsonl
```

判断原则：

- 心跳应约每 15 分钟增长；
- 切换应用后前台事件应增长；
- 息屏和解锁后屏幕事件应增长；
- `incoming` 中前台或屏幕文件为 0 行不一定是故障；
- 当天归档行数不应因上传较小文件而减少。

## 8. 专项故障定位

| 现象 | 优先检查 |
|---|---|
| 公网和本机健康检查都失败 | `phone-usage-receiver.service` |
| 本机成功、公网失败 | `tailscaled.service` 与 `tailscale funnel status` |
| 健康检查成功但没有上传 | 手机网络、Clash、Automate 流程与请求路径 |
| 返回 401 | 手机三个请求头中的上传密钥 |
| 返回 400 | JSONL、时间戳和服务器日志中的错误行号 |
| 返回 `NoSuchFileException` | 手机当天文件是否创建、写入与上传路径是否一致 |
| 心跳超过 30 分钟不增长 | 手机后台保活、网络、流程是否被停止 |
| 归档行数突然减少 | 是否错误恢复了旧版 `receiver.py` |

### 8.1 查看接收服务日志

```bash
systemctl status phone-usage-receiver.service --no-pager -l
journalctl -u phone-usage-receiver.service -n 100 --no-pager
```

### 8.2 重启接收服务

```bash
sudo systemctl restart phone-usage-receiver.service
systemctl is-active phone-usage-receiver.service
curl http://127.0.0.1:8765/health
```

重启后还应让手机执行一次三文件上传，并确认三次均返回 200。

### 8.3 归档异常时

先检查，不要删除或覆盖：

```bash
wc -l /home/conrad/phone_usage/archive/YYYY-MM-DD/*.jsonl
ls -l /home/conrad/phone_usage/receiver.py*
journalctl -u phone-usage-receiver.service --since today --no-pager
```

当前接收器使用合并去重，正常情况下归档只增不减。若程序版本错误，应先恢复最近验证过的 `receiver.py`，再从手机日期文件或旧文件补传。

## 9. 安全与改进边界

### 9.1 必须保持的安全边界

- 8765 只监听 `127.0.0.1`；
- Funnel 只代理手机数据接收服务；
- 上传接口始终要求密钥；
- `token.txt` 权限保持 600；
- 路由器不转发 8765；
- Cockpit、File Browser 和 SSH 不接入 Funnel；
- 文档和 Git 不保存真实密钥。

### 9.2 当前尚未完成

- 手机跨午夜时自动补传昨天文件；
- 手机端自动删除 14 天前文件；
- 三个 HTTP 状态码的自动判断；
- 30 分钟无心跳的 PushPlus 告警；
- 应用包名分类和时长计算；
- 半小时、每日汇总；
- Windows ActivityWatch 合并；
- 原始归档的独立备份。

### 9.3 建议改进顺序

1. 完成昨天文件终结上传；
2. 增加 HTTP 状态码判断；
3. 增加 30 分钟无心跳告警；
4. 增加手机端 14 天自动清理；
5. 建立只读汇总程序；
6. 建立归档备份；
7. 最后接入 ActivityWatch 和可视化。
