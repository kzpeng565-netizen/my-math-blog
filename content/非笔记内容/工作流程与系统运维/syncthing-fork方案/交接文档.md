## 2. 处理过的问题与解决方案

### 2.1 Obsidian 启动缓慢、侧边栏几乎卡死

表现：笔记文件导航和设置难以打开，但已经加载的文本仍可编辑。旧渲染进程持续高 CPU，曾在 5 秒采样中消耗 5.84 秒 CPU。诊断时磁盘统计约有 13,812 个文件；该数字不等于 `vault.getFiles()` 的实际返回数量。

旧版 0.1.0 的关键路径：

```text
每个 create / delete / rename
    → 单独创建一个 750 ms 定时器
    → refreshConflictsOnly()
    → 遍历 vault.getFiles() + 列根目录 + 递归扫描 .obsidian
```

旧事件路径没有防抖、任务合并或扫描互斥；20 秒 API 轮询也会再次全量扫描。批量同步/初始化产生大量事件时，扫描工作会堆积。Make.md 导航器同样依赖文件事件，是明显受影响的界面；不能仅凭现象认定 Make.md 是唯一根因。

处置：

1. 用户禁用 `vault-sync-monitor` 后确认恢复正常，支持旧插件为触发因素。
2. 发布 0.1.1：事件改为维护冲突路径集合，普通事件不再触发全库扫描。
3. 加入共享扫描 Promise、五分钟扫描缓存和扫描期间事件重放。
4. 部署两端并检查产物一致性。

**精确说法**：0.1.1 是“增量缓存 + 扫描互斥”，不是已经实现了定时防抖或界面批量刷新。真正的冲突事件仍会立即刷新 UI。

### 2.2 API 密钥未选择

插件配置中保存的是 SecretStorage **条目名称**，不是密钥值。两端都使用条目名 `syncthing-api`，但每台设备应存放它自己的 Syncthing API 密钥。

处理方式：在本机 Syncthing GUI 的 API 密钥设置中取得本机密钥，然后在该设备 Obsidian 的 SecretStorage 中创建/选择对应条目。只复制 `data.json` 不会完成另一设备的密钥配置。不要将密钥正文写进交接文档、Git、截图示例或同步目录。

插件只发送 GET，但 Syncthing API 密钥本身不是由插件限制权限的“只读令牌”。

### 2.3 平板 Tailscale 在线，但 Syncthing 服务离线

实际排查发现 Syncthing-Fork 应用/原生引擎未运行，`127.0.0.1:8384` 无监听。启动应用后，运行条件页显示当前网络是计量 Wi-Fi，而对应运行选项关闭。

处理方式：

- 打开 Syncthing-Fork → 设置 → 运行条件。
- 开启“使用按流量计费的 Wi-Fi 时运行”，返回主页面让运行条件重新评估。
- 之后确认本机 8384 端口开始监听。
- 本次没有开启移动数据同步。计量 Wi-Fi 可能使用手机热点流量，后续应留意大附件传输。

Tailscale 在线不保证 Syncthing 引擎也在运行；“仅 Tailscale”指设备不在同一局域网、仍有可用底层网络，不是无网络同步。

### 2.4 HTTP 307 与 HTTPS 自签名证书

服务上线后，插件首先收到 HTTP 307。平板本机 `curl` 实测响应：

```text
http://127.0.0.1:8384/rest/noauth/health
    → 307，Location 指向相同路径的 https://127.0.0.1:8384
```

临时把平板插件 endpoint 改为 HTTPS 后，Obsidian 请求报 `SSLHandshakeException` / `Trust anchor for certification path not found`，确认是自签名证书不被信任。

最终配置：

1. 在 Syncthing-Fork 内置 Web GUI 中，进入“操作 → 设置 → GUI”。
2. 关闭“使用 HTTPS 连接到 GUI”，保存。
3. **保持 GUI 仅绑定 `127.0.0.1:8384`，不打开远程 GUI 访问。**
4. 将插件 endpoint 恢复为 `http://127.0.0.1:8384`。
5. 平板本机健康接口直接返回 HTTP 200；重启 Obsidian 后插件成功读取状态。

这是回环管理接口的配置调整，不是关闭设备间文件传输加密。不要将上述 HTTP 配置照搬到 `0.0.0.0`、局域网或 Tailscale 地址，也不要让插件忽略 TLS 证书校验。

## 3. 当前插件架构

### 3.1 文件与模块

插件目录：`D:\mathblog\quartz\content\.obsidian\plugins\vault-sync-monitor`

| 文件/模块 | 职责 |
| --- | --- |
| `source.js` | 源码，主插件、设置页、弹窗和冲突算法均在一个文件内 |
| `main.js` / `main.js.map` | Obsidian 实际加载的 CommonJS 产物及 source map |
| `manifest.json` | id `vault-sync-monitor`，版本 0.1.1，最低 Obsidian 1.11.0，允许移动端 |
| `styles.css` | 状态栏、设备卡片和冲突面板样式 |
| `data.json` | endpoint、文件夹 ID、SecretStorage 条目名、轮询和通知偏好 |
| `versions.json` / `README.md` | 兼容版本映射、功能和安全说明 |
| `VaultSyncMonitorPlugin` | 生命周期、事件监听、缓存、请求和 snapshot 分发 |
| `SyncStatusModal` | 订阅 snapshot，显示文件夹、设备、冲突；打开时请求刷新 |
| `VaultSyncMonitorSettingTab` | 编辑设置、选择 SecretStorage 条目、测试连接 |

### 3.2 两条数据路径

```text
本机 Syncthing REST ──20 秒轮询──→ refresh() / performRefresh()
                                           │
Vault create/delete/rename → conflictPaths ─┤
启动/手动/缓存过期 → 全量扫描 + 事件重放 ────┤
                                           ↓
                                      setSnapshot()
                                           ↓
                             状态栏 + 订阅中的弹窗 + 新冲突通知
```

API 路径：

- 通过 Obsidian `requestUrl()` 请求，只允许 localhost、127.0.0.1、::1 等回环主机。
- 从 SecretStorage 读取本机密钥，放入 `X-API-Key` 请求头。
- 一轮并行读取 system/status、config/folders、db/status、config/devices、system/connections、stats/device，再查询共享远端设备的 db/completion。
- `refreshInFlight` 合并重叠的状态刷新。
- 没有密钥时仅尝试 `/rest/noauth/health`，区分未配置与服务不可达。

冲突路径：

- 只依据路径名识别 `.sync-conflict-`，排除 `.stversions`、`.trash` 中的副本；不读取 Markdown 正文、手写笔画或附件内容。
- `conflictPaths: Set<string>` 保存当前已知冲突路径。
- `recordConflictMutation()` 接收 create/delete/rename；集合实际变化时才 `publishCachedConflicts()`。
- 普通 create 不遍历全库；delete/rename 会遍历**当前冲突集合**以处理文件及目录变化。因此不能笼统说所有事件都是 O(1)。
- `getConflicts()` 在启动、显式手动刷新，或缓存超过 `5 * 60 * 1000` 毫秒时请求全量扫描。五分钟是缓存期限，实际由下一次刷新触发，不是额外的固定扫描定时器。
- 全量扫描遍历 `vault.getFiles()`、根目录，并递归扫描 `vault.configDir`（当前 `.obsidian`），递归深度上限 8。
- `conflictScanInFlight` 让同时调用共享一轮扫描；扫描期间把事件写入 `pendingConflictMutations`，结束时重放后替换缓存。

### 3.3 当前实现的边界

以下为 2026-08-31 源码核对发现，不表示都已在设备上复现：

- 大量**真正冲突**仍可能导致频繁排序、通知和弹窗重绘，尚无 UI 合批机制。
- 隐藏目录变化未必有普通 Vault 事件，依赖下一次全量扫描兜底；深层目录超出上限不会遍历。
- `safeList()` 将列目录失败当作空列表，暂未显示“扫描不完整”，存在误报无冲突的风险。
- 网络请求前取得的冲突数组可能在请求等待期间过时；后续 `setSnapshot()` 可能暂时覆盖事件路径刚发布的新状态，需加回归测试。
- 扫描期间事件队列无显式大小上限；卸载只清理轮询和监听订阅，尚无在途异步任务的失效标记。
- `folderPhase()` 只使用本机文件夹状态和本地冲突判定 healthy，不使用远端完成度。因此“已同步”以及“已连接设备均无待同步数据”的文案不能作为所有远端都完成的证明。
- 插件未实现 AI 合并、双端内容比较、版本恢复或冲突文件删除。

### 6.2 快速排障顺序

| 现象 | 先检查什么 |
| --- | --- |
| 再次侧栏卡死 | 保存内容，临时禁用 Vault Sync Monitor 做对照；查看进程 CPU，确认实际加载版本，避免直接清缓存/删笔记 |

| 面板已同步，但另一端缺文件 | 逐一检查远端 completion、连接和 Need 数据，不只看顶部 healthy 标签 |
