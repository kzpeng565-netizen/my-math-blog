# 半小时行为解释系统——架构与维护

<!-- ai_provenance: source=codex; date=2026-07-24; verification=checked; retrieved_notes="" -->

## 1. 第一版目标

系统每半小时分别清洗电脑和手机使用数据，保存两份独立事实摘要。DeepSeek V4 Flash 第一次调用把跨设备证据解释成语义时间段，程序据此计算工作—娱乐混杂指标，第二次调用负责解释结果。系统最后通过 PushPlus 微信公众号渠道发送一份短核验消息；不弹窗、不修改计划、不调用 Cold Turkey 或手机管控。

```text
电脑 ActivityWatch SQLite ─→ computer_facts ─┐
                                             ├→ DeepSeek语义时间线
手机 foreground/screen/heartbeat ─→ phone_facts ─┘
                                                      ↓
                                             程序计算工作—娱乐混杂
                                                      ↓
                                             DeepSeek解释 → 微信核验
```

==系统现改为每小时 `08` 和 `38` 分运行，分析刚结束的半小时，为手机约15分钟一次的上传留出时间。==

## 2. 为什么保留两个独立事实层

- 电脑 AFK 不等于休息，可能正在使用手机；
- 手机亮屏不等于娱乐，可能是在通信、查资料或操作工具；
- 两套采集器的缺失和延迟不同；
- 独立保存后，整天分析可以复用，不必再次读取全部原始事件；
- AI 判断错误时，可以定位是电脑提取、手机提取、跨设备比较还是模型解释的问题。

跨设备层只计算时间重叠，例如“电脑非 AFK 且手机亮屏多少分钟”，不直接判断分心。

## 4. 输出位置

树莓派运行副本：

```text
/home/conrad/workspace/activitywatch-advisor
```

输出：

```text
data/
├── computer_facts/YYYY-MM-DD/HH-MM.json
├── phone_facts/YYYY-MM-DD/HH-MM.json
├── combined_facts/YYYY-MM-DD/HH-MM.json
├── semantic_timelines/YYYY-MM-DD/HH-MM.json
├── mixing_metrics/YYYY-MM-DD/HH-MM.json
├── ai_reports/YYYY-MM-DD/HH-MM.json
├── ai_reports/YYYY-MM-DD/HH-MM.md
├── pushplus_receipts/YYYY-MM-DD/HH-MM.json
└── state/processing-state.json
```

`computer_facts` 和 `phone_facts` 是原始事实摘要；`semantic_timelines` 是可复核的 AI 语义解释；`mixing_metrics` 是程序从语义时间线确定性计算的结果；`ai_reports` 只负责最终说明。整天分析可以复用前三层，不必重新读取所有原始事件。

首个时段的全部输出约为 29 KB。按每天 48 个时段粗略估算约为 1.4 MB/天、0.5 GB/年，当前不需要为了节省空间删除事实层。积累一个月后再根据真实增长量决定是否压缩旧 JSON。

## 5. 清洗原则

电脑端：

1. 以 `(starttime, data)` 合并 aw-sync 的增长版本；
2. AFK冲突时，以更晚开始的状态为准；
3. 只把 `not-afk` 时段计入窗口活动；
4. 浏览器优先使用 Web Watcher 的域名和标签页标题；
5. Web Watcher缺失时退回窗口标题，不强行分类。

手机端：

1. 合并 archive 与 incoming，并按事件内容去重；
2. 由 screen 事件重建亮灭屏时段；
3. 只有亮屏后出现的新 foreground 事件才认定为当前前台应用；
4. 用 heartbeat 判断采集器是否仍然在线；
5. 不把亮屏、微信或哔哩哔哩直接解释为行为动机。

发送给 AI 前会清除标题中的未读数量、浏览器后缀、邮箱、手机号和长标识符。完整 URL 不发送，只保留域名。

## 6. 密钥

真实 API 密钥不在本目录中。树莓派使用：

```text
/home/conrad/.config/activitywatch-advisor/env
```

该文件权限必须为 `600`。`.env.example` 只有占位符。

PushPlus 用户令牌单独保存在：

```text
/home/conrad/.config/activitywatch-advisor/pushplus.env
```

该文件同样为 `600`。发送代码把渠道固定为 `wechat`，不会读取 Windows 上原先的 `app` 渠道设置。同步响应只表示 PushPlus 已接收请求，因此每次发送的流水号会写入 `pushplus_receipts` 供排查。

当前只有“树莓派向微信发送报告”的单向链路。微信公众号中的回复不会自动写回系统，核验结果暂时在 Codex 中反馈。

## 10. 第二版状态核验

==用户核验后确认，第一版叙述型报告没有直接回答“工作多久、休息多久、碎片化如何”，并且重复输出了多条不会改变结论的固定免责声明。第二版改为指标先行：先输出观察到的设备时间，再输出互斥的工作、休息、其他和无法判断估计，最后结合切换次数与连续块解释碎片化。==

==原来的 `browser_web_context_coverage` 被证明命名和用途错误。它实际计算的是窗口采集器与网页插件事件持续时间的精确重叠，而不是标签页识别率。20:30—21:00 的原始数据中，网页插件记录了页面标题，但包含大量0秒快照和不连续时长。第二版保留 `web_watcher_exact_time_overlap` 作为内部诊断，并使用窗口标题与本时段 `observed_pages` 匹配来恢复域名。该时段的浏览器标题覆盖率为97.8%，域名关联率为100%。==

==手机心跳约每15分钟一次。第一版在21:03启动，早于21:03:59到达的下一批手机数据，因而把本时段手机亮屏低估为30秒。第二版把定时器推迟到 `08` 和 `38` 分，并把心跳阈值改为与实际周期相符；只有真正失联才进入报告。重新处理后，手机亮屏为6.02分钟。==

==第二版增加确定性指标：电脑活跃/AFK、手机亮屏、电脑与手机同时活跃、无设备交互、上下文块数量、切换次数、短块数量、持续块数量和最长连续上下文。AI只能对工作/休息语义进行估计，确定性数字会由程序覆盖，且报告必须通过分钟总和与时间线一致性校验；失败时会要求模型自动修正。==

==20:30—21:00 的首次第二版回放得到：电脑活跃26.72分钟、手机亮屏6.02分钟、同时活跃2.73分钟；有15个有意义的上下文块、14次切换、10个不足一分钟的短块、1个至少五分钟的持续块，最长连续上下文11.21分钟。当时AI仍把电脑AFK期间使用微信/QQ误算为休息；该语义结果已经被下面的用户确认规则取代。==

## 11. 第三版：工作—娱乐混杂

<!-- ai_provenance: source=codex; date=2026-07-24; verification=user-confirmed-design; retrieved_notes="" -->

==用户确认：衡量重点不是窗口或应用切换次数，而是工作与娱乐是否混杂。工作期间十秒左右回复消息属于正常通信；ChatGPT、浏览器、Obsidian、数学视频等服务于同一任务时也不能算偏离。工作过程中被 AI 判断为娱乐且持续严格超过30秒，才构成一次娱乐偏离。==

第三版把原来的单次 AI 解释拆成两步：

1. 第一次 AI 调用结合电脑、手机、网页标题和前后各5分钟辅助上下文，把报告时段切分为互斥的 `work`、`entertainment`、`brief_communication`、`rest`、`other`、`uncertain`；
2. 程序校验时间线完整性与确定性休息区间，计算娱乐偏离次数、总时长、最长偏离、工作—娱乐转换、返回工作情况和最长连续工作；
3. 第二次 AI 调用只解释已经校验的时间段和指标，不重新计算分钟数。

混杂等级只统计工作过程中的娱乐偏离：

| 等级 | 规则 |
|---|---|
| `none` | 没有严格超过30秒的工作内娱乐偏离 |
| `low` | 1次，偏离总计不超过2分钟 |
| `medium` | 总计超过2分钟但不超过5分钟，或出现2—3次 |
| `high` | 总计超过5分钟，或出现至少4次 |

纯娱乐、工作结束后自然转入娱乐、短暂通信和同任务工具切换都不参与混杂等级。短暂通信位于同一工作任务中间时，程序会把前后工作视为连续，不会缩短最长连续工作时长。
